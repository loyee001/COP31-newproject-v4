# ShadePath 方法与数据边界

本网页用确定性计算解释“有限预算下，树种在哪里能给校园步道网络增加更多荫凉”。没有连接生成式模型、在线天气服务或校园传感器。界面中的分析来自几何和规则计算；校园名称查询只用于查找地理位置，不会从图片中自动识别建筑或步道。

## 坐标与示例数据

校园地面是平面米制坐标系，x 向东，y 向北。网页默认有四条步道：主步道 `(22,28) → (182,28) → (182,76)` 长 208 m，横向步道 `(23,58) → (182,58)` 长 159 m，图书馆支路 `(76,58) → (76,75)` 长 17 m，活动区支路 `(135,58) → (135,86)` 长 28 m。唯一物理路段合计 412 m，有三个交叉口。引擎单路线示例仍保留原 208 m 路线作为兼容数据。

`paths` 是路网数据源，每条包含 `id、name、points、width、demand`。只有完全没有 `paths` 属性时才读取旧 `route`；`paths:[]` 表示尚未标注步道，不自动填入示例路线。导入图片后需校准米制尺寸，并在北向上图片中手动标注路线；图片本身不提供建筑高度或已有树木数据。

默认纬度 31.23°、经度 121.47°、时区 UTC+8，日期为 2026-06-21。此位置仅作为太阳计算参数，不表示示例建筑位于某个真实校园。建筑、树木、天气与人流均为合成示例。

## 太阳与阴影

太阳位置采用 NOAA 太阳位置计算方法，考虑经度、时区、均时差、太阳赤纬和大气折射。太阳方位角由正北顺时针计量；太阳高度角决定阴影投影的长度。太阳处于地平线下时不把“没有阳光”计为新增种树收益。

建筑近似为从二维轮廓竖直拉伸的实体，其地面阴影由底面轮廓与沿背光方向移动的顶面轮廓求凸包。此近似适用于凸形示例建筑；凹形建筑宜先拆成凸形体块，以免夸大阴影。

树冠近似为不透光球体的投影椭圆，半短轴为 `r`，半长轴为 `r / sin(太阳高度角)`，中心沿背光方向偏移 `h / tan(太阳高度角)`。这里 `h` 是树冠球心高度，不是树顶高度；示例球心 8 m、半径 4.6 m，对应树冠顶部 12.6 m。它是理想几何近似，不能表达树叶透光、真实枝条或冠层孔隙。

建筑阴影和树冠阴影按并集判定，同一点不会因为多个阴影重叠而重复获得收益。网页地图中的阴影为选定瞬时的投影；步行指标则按沿途抵达时刻判定，两者时间口径不同。

## 路网拓扑、到达时刻与共享路段

引擎把交叉口、端点及共线重叠的边界拆分为唯一物理路段。同一段被多条路径引用时只计一次物理长度；其通行净宽取覆盖路径宽度的最大值。二维交叉按同一地面交叉口处理，未表达天桥或地下通道。

每段按不超过 0.5 m 的间隔采样，以梯形积分分配真实长度，避免端点多算。每条路径都从自己的第一个点，在选定时刻出发；采样位置的抵达时间为“出发时刻 + 该路径累计距离 / 1.15 m/s”。因此同一个共享位置可能有多个抵达时刻，各自重新计算太阳、阴影和热环境。

共享路段的遮荫结果按各条路径的 `demand` 归一化平均，即 `Σ(demand × 遮荫指示值) / Σ demand`；同一路径重复经过同一边时，先在它自己的多次经过之间平均。全网遮荫率再按唯一物理长度积分，避免重复画一条路线就重复计算长度。每条路径的独立指标则保留该路径自己的完整长度与抵达时间。地图上的共享段颜色混合表示不同抵达时刻的平均结果，不表示树叶透光率。

基线包含建筑与既有树；种植后新增树与基线一起判定。新增收益只算同一条件下的净新增遮荫。全网 `walkMinutes = 唯一物理长度 / 1.15 / 60` 是等效遍历时间，不是一名学生连续走完整个网络的行程；每条路径的 `walkMinutes` 才是沿该路径的行走时间。当前采样覆盖步道中心线，路宽用于种植净空约束，不把指标解释为整个路面面积的遮荫率。

日夜状态按全部抵达时刻采样判断，不能只看出发瞬间。`daylightFraction` 是有阳光的加权时间比例，`anyDaylight` 表示至少一段白天，`fullNight` 表示全程夜间。跨越日出或日落时保留部分白天结果；夜间不产生新增种树收益。空路网返回零长度、零收益和空方案。

## 预算与种植

`ShadeEngine.candidates(campus, settings)` 结合两类位置：沿每条路径每 8 m、两侧偏移 `max(3.5 m, 路宽/2 + 1 m)` 的路边候选，以及按当前太阳方向逆投影得到的候选。逆投影先沿路线确定期望树影中心，再根据沿途抵达时刻的太阳高度、方位和冠心高度反求树干位置，并加入沿路线法向的偏移备选。早晚影子较长，树干可离步道更远；中午影子短，树位相应靠近路线。交叉口及其附近加入额外锚点，全部路径的候选位置在全网统一去重。

所有候选都需满足同样的地块、步道、树干与建筑约束。还检查树冠球体与建筑棱柱是否相交：使用建筑高度处的球冠截面计算水平净空，避免树冠穿过墙体。矮屋顶低于树冠且空间不相交时允许树冠越过屋顶，不把树冠地面投影一律当作实体碰撞。

示例每棵树成本为 $95（产品文档设定的采购与三年养护合计假设）。实际采购前需替换为真实报价。

默认 `settings.optimizationMode='current'`，只有当前选定的一个出发时刻，权重为 1；所有路径从各自起点出发。每个采样点仍按实际抵达时刻计算太阳，目标是增加全网加权遮荫分钟数。改变时刻后，自动方案重新生成候选并重新选择树木；手动方案保持用户树位，重新评估同一布局。

开发者可显式设置 `settings.optimizationMode='lunch'`，恢复产品原文的午间多时段目标：11:50、12:20、12:50 三组出发时间，权重为 0.25、0.45、0.30。每组在中心时刻前后 `−8、−4、0、+4、+8` 分钟取五个时间片，每片权重为组权重的五分之一。网页当前不提供午间模式切换控件；它是引擎 API 的可选模式，不是网页默认行为。

两种目标都在唯一物理路段上积分。每条共享边的人流权重取覆盖它的不同路径 `demand` 的算术平均值；边内不同路径抵达时刻按各自需求占比平均。目标可写作 `Σ边 平均需求 × ∫(种植后遮荫 − 基线遮荫) dx / (1.15 × 60)`，多出发时段时再乘对应时段权重。这是相对需求权重，不是实测人数。

算法逐棵选择单位成本带来净新增加权荫凉分钟数最高的候选树，直到预算不足或没有正收益。所有路径共用一个预算、一组树；交叉口的一棵树可同时服务多条路径，只付一次成本。同一采样元素被多个树影覆盖仍只计一次收益。`auditPlan` 与优化器使用同一口径。`treeServices` 中的服务路径表示该树在这些路径上覆盖了基线未遮荫的位置，不代表移除其他树后它的独占边际收益。

这是带几何约束的贪心近似，不保证全局最优。预算上限是可用资金，最终实际费用可能低于预算；手动方案可暂时超预算，但应显示差额，不能当作预算内方案。

“91% 收益方案”从满预算贪心序列中取达到其新增加权收益 91% 的最短前缀。保留比例由当前数据计算，树数与费用可能随季节、纬度变化。它不是固定“18 棵”，也不等同于正式检测收益曲线拐点。

全天曲线在自动和 91% 模式下，会在每个图表时刻重新生成该时刻的方案。因此它展示的是“各时刻分别优化后”的收益，不代表一组固定树木能同时达到整条曲线。手动模式的全天曲线才使用同一组树位逐时评估。

## UTCI 热环境计算

主结果采用 UTCI 官方操作性六阶多项式近似（Bröde et al., 2012），不是原产品说明中的线性代理式。多项式由 `Ta、10 m 风速、Tmrt−Ta、水汽压` 四个变量组成，共 210 个单项式；总次数最高为六阶。

```text
UTCI = Ta + offset(Ta, v10m, Tmrt−Ta, vapourPressure_kPa)
```

Ta 与 Tmrt 的单位为 °C，风速为地面上 10 m 高度的 m/s，相对湿度输入为百分比。相对湿度通过 Hardy 饱和水汽压公式换算为 hPa，再除以 10 得到多项式所需 kPa。1.15 m/s 步行速度只用于路线时间积分，不能当作 UTCI 的气象风速。

适用范围为气温 −50 至 50°C，`Tmrt−Ta` 为 −30 至 70°C，10 m 风速 0.5 至 17 m/s，相对湿度 0 至 100%，且水汽压不超过 5 kPa。范围端点包含在内。超过范围、缺失或非有限输入返回无效值，不强制压到边界，也不偷偷改用代理式。仅对相对湿度换算在 5 kPa 边界产生的浮点舍入误差保留 `10⁻¹² kPa` 容差。

网页初始输入显式设置为 `Ta=32°C、RH=55%、v10m=1.2m/s`，这些值覆盖引擎的缺省气象设置，不随日期、地点或时刻自动改变；当前界面不提供天气控件，也没有接入天气服务。恢复的数据文件可以显式提供其他气象覆盖值。开发者直接调用引擎且未提供覆盖值时，气温使用 `29.8 + 2.5 × cos((分钟−870)/1440 × 2π)`，相对湿度 55%，10 m 风速 1.4 m/s。

令 `s=max(0,sin(太阳高度角))`，示例暴晒 Tmrt 为 `Ta + 14.5×s`，树荫/建筑阴影为 `Ta + 1.5×s`。这些辐射参数为演示假设，不是辐射传输解或实测值。遮荫只改变辐射项，没有模拟树木蒸腾对空气温度的影响。

热负荷为 `Σ max(UTCI − 26, 0) × 分钟数`，单位为 °C·min；它是便于比较方案的模型积分，不是生理热量（焦耳），也不是健康诊断。采用标准多项式并不代表气象输入、现场模型或个人体感已经得到验证。

原说明中的 `Ta + 0.12e − 1.05v + 0.45(Tmrt−Ta)` 仅作为明确标识的简化代理对照，不冒充 UTCI。

## UTCI 数值验证

`src/thermal.js` 的系数移植自 MIT 许可的 pythermalcomfort，并与 UTCI 官方 Fortran a0.002 原始系数逐项核对；210 个单项式全部一致到浮点精度。独立 ECMWF thermofeel 实现生成 800 组有效输入参考值，涵盖气温、辐射温差、风速和湿度组合。当前 JavaScript 最大绝对差约 `3.27×10⁻¹³ °C`；另验证文档示例 `Ta=Tmrt=25°C、v=1m/s、RH=50% → UTCI≈24.6°C`。

此检查证明公式移植的数值一致性，不代表真实校园模型的预测精度。参考数据、源代码哈希及复现脚本在 `tests/reference/`，许可证同时保留在源码和 `docs/licenses/`，离线单文件中也包含许可证。

## 导出与恢复契约

导出保留全部路径源几何、当前真正参与计算的纬度、经度、数值时区、天气覆盖值、优化模式与预算；同时保留 IANA 时区名称及位置来源等元数据。实际计算用的三项位置数值优先于初始校园值。校园 JSON 只包含标量、各路径指标和树木服务摘要，不重复写入 `profile、mapProfile、network` 采样/拓扑大对象；恢复时重新生成这些数据。`scenario.settings.optimizationMode` 记录采用 `current` 还是 `lunch`；`trees` 包含既有树与新增树，`scenario.baselineTreeIds`、`scenario.addedTreeIds` 明确各自身份。

`ShadeEngine.restoreScenario(exported)` 返回 `{campus, trees, settings, budget}`，其中 `campus.trees` 只保留既有树，新增树独立返回，保证重新计算“种植前”时不混入新增树。重复树 ID、找不到的新增树 ID、无效太阳参数或预算会被拒绝。网页支持校园 JSON 导入恢复，也支持 PNG/JPG/WebP 图片导入后人工标注多条步道。图像内容不会自动成为几何遮挡物。本交付不包含 Godot 页面或互通工程。

## 未包含的效应

示例未模拟多年树冠生长、蒸腾、地表反射、地形、局地风场、复杂楼体、云影、透光叶隙、季节落叶、地下管线或树种适生性。方案也未校验真实消防通道、种植许可或工程施工条件。

原说明中的 16%/87%、36.9°C/32.9°C、18 棵等数值没有随文档提供原始数据和校准材料，本交付不声称复现。所有新结果为当前合成示例的计算结果，非实测。
